# Zed WIT extension 0.5.3

This release introduces Chiploom's implementation of the WebAssembly Interface Types (WIT) extension for Zed, succeeding the original extension by Valentine with their permission.

It provides modern WIT language support through syntax-aware editing, native language-server integration, document formatting, semantic navigation, and verified native server distribution.

Version `0.5.3` supersedes the unpublished `0.5.0`, `0.5.1`, and `0.5.2` release candidates. The first two were blocked during protected release-policy validation before tag creation. The `0.5.2` attempt created a protected Git tag and unpublished draft release, but failed during draft asset-integrity verification before publication.

The publishing corrections included in `0.5.3` address these failures without weakening repository protections or changing the extension's language features.

## Highlights

### Modern WIT language support

- Syntax highlighting using the pinned Bytecode Alliance Tree-sitter WIT grammar.
- Support for packages, interfaces, worlds, resources, types, functions, and annotations.
- Recognition of modern WIT grammar constructs, including async functions, futures, streams, maps, and nested packages.
- Automatic `.wit` file recognition and WIT Markdown code-fence support.
- Bracket matching, automatic indentation, code outlines, and Vim text objects.
- Snippets for packages, interfaces, worlds, types, functions, imports, exports, and `use` declarations.

### Native WIT language server

- Native language server built on upstream `wit-parser` semantics.
- Parser-backed syntax, name-resolution, and type diagnostics.
- Scope-aware completion, including local types and imported declarations.
- Hover information, go to definition, and find references.
- Safe quick fixes for unresolved types when suitable candidates exist in scope.
- Multi-file package analysis, including sibling files and supported local `deps/` layouts.
- Unsaved-buffer support for package files and dependencies.
- Incremental document synchronization and diagnostics updates.

### Document formatting

- Topiary-based document formatting.
- Preservation of comments and documentation.
- Consistent, idempotent formatting.
- Configurable spaces and tabs.
- Refusal to format syntax-invalid documents rather than risk producing incorrect output.

### Native server installation and distribution

The extension uses the published, immutable WIT Language Server `v0.1.2`.

- Automatically downloads the appropriate native executable when no configured language server is available.
- Verifies executable integrity using SHA-256 checksum sidecars.
- Caches verified downloads to avoid unnecessary network requests.
- Detects corrupted or incomplete executable caches and missing checksums, then recovers automatically.
- Supports explicitly configured or otherwise discoverable local language-server installations.

Supported native language-server targets:

| Platform  | Architecture  |
| --------- | ------------- |
| macOS     | ARM64, x86_64 |
| Linux GNU | ARM64, x86_64 |
| Windows   | x86_64        |

The extension and native language server use independent release version streams. Extension `0.5.3` remains explicitly pinned to WIT Language Server `v0.1.2`.

## Release infrastructure and reliability

This release incorporates the project's protected publishing infrastructure and the corrections identified during the preceding release attempts.

### Protected release workflow

- Version-aware Rust `xtask` commands for release planning, preparation, validation, and protected publication.
- Independent release streams for the native language server and Zed extension.
- Human-reviewed release preparation through protected pull requests.
- Verification of the exact reviewed source commit before publication.
- Protected GitHub Actions CD with release-environment restrictions.
- Verification of immutable-release enforcement and required repository protections.
- Validation of release metadata, dependencies, and GitHub Release state.
- Fail-closed behavior when release authorization, identity, or protection requirements cannot be established.

### Manifest and lockfile integrity

Release preparation now explicitly verifies that version updates preserve the existing Cargo manifests and lockfile structure.

- Restricts manifest changes to the intended version transition.
- Preserves package metadata, workspace configuration, dependency declarations, and extension identity.
- Verifies that `Cargo.lock` changes only the selected package's version.
- Rejects missing or duplicate package records, unexpected dependency changes, and malformed lockfiles.
- Covers both extension and native language-server release preparation.
- Includes disposable-workspace regression tests exercising actual Cargo release preparation.

### Tag-protection policy compatibility

The tag-policy preflight handles GitHub API responses that differ according to the caller's authorization and timestamp serialization.

- Accepts permission-dependent redaction of `bypass_actors` only for the independently audited ruleset revision.
- Requires active `v*` tag protection against updates, deletion, and non-fast-forward changes.
- Rejects unexpected bypass actors, missing protections, and unreviewed ruleset revisions.
- Recognizes both verified timestamp representations of the same audited ruleset revision:
  - `2026-10-06T21:11:44.860-04:00`
  - `2026-10-07T01:11:44.860Z`
- Continues rejecting genuinely changed timestamps and ruleset configurations.
- Preserves the restricted authorization model without introducing an administration-write credential.

### CD workflow identity verification

- Reconciles temporarily incomplete GitHub Actions run metadata through bounded retries.
- Queries the exact run ID returned by the confirmed dispatch.
- Immediately rejects explicitly mismatched workflow run IDs or source commits.
- Requires complete workflow identity verification before accepting a successful publication.
- Never treats a requested or running workflow as a completed release.

### Draft release verification and recovery

The previous `0.5.2` publication attempt exposed an incompatibility between GitHub's release-by-tag REST endpoint and unpublished draft releases.

Protected CD now resolves draft releases through their numeric GitHub release IDs rather than relying on an endpoint intended for published releases.

- Resolves the release using the authenticated GitHub CLI.
- Retrieves the corresponding release through GitHub's REST API using its numeric database ID.
- Verifies that the resolved release ID and tag match the expected release.
- Rejects malformed IDs, inconsistent release metadata, and unexpected release identities.
- Uses the same verified lookup for draft asset-integrity checks and the final pre-promotion validation.
- Preserves existing asset-count, SHA-256 digest, uploaded-state, release-title, and source-commit checks.
- Retains separate post-publication verification, including immutable-release enforcement.
- Adds offline regression tests for draft-only HTTP 404 behavior, identity mismatches, and malformed lookup responses.
- Does not require broader GitHub token permissions or changes to repository protection policies.

These corrections retain strict release integrity checks while allowing legitimate unpublished drafts to be validated through supported API paths.

## Known limitations

- Package dependency discovery is restricted to supported local file and directory layouts.
- Remote dependency downloads and encoded binary component dependencies are not supported.
- Some newer syntax recognized by the grammar remains gated by upstream WIT semantic support.
- Native language-server binaries outside the five supported target combinations are not distributed.
- This GitHub extension release does not itself publish or update the Zed extension registry.
